# tango-mqtt

scadawire/tango-controls integration to Mqtt servers/devices

This device driver integrates to IOT devices, see also https://mqtt.org/.

# Structure

The integration makes use of the tango python binding to implement device driver functionality.
See also https://tango-controls.readthedocs.io/en/latest/development/device-api/python/index.html

The mqtt specific functionality is covered by the mqtt paho python package.
See also https://pypi.org/project/paho-mqtt/

# Requirements

The device server supports 5.0, 3.1.1, and 3.1 of the MQTT protocol, selected through the `protocol`
property. The integration allows for authenticated and unauthenticated connections.

# Device properties

| Property | Default | Meaning |
| --- | --- | --- |
| `host` | `127.0.0.1` | Broker address |
| `port` | `1883` | Broker port |
| `username` | `` | Username; a password is optional, brokers authenticating on the username alone are supported |
| `password` | `` | Password |
| `client_id` | `` | MQTT client id, generated by paho when empty |
| `clean_session` | `true` | `false` asks the broker to keep the session across reconnects, which needs a non empty `client_id` |
| `protocol` | `3.1.1` | `3.1`, `3.1.1` or `5.0` |
| `keepalive` | `60` | Keepalive interval in seconds |
| `default_qos` | `0` | QoS used by every attribute and publish that does not name one |
| `default_retain` | `false` | Retain flag used by every attribute and publish that does not name one |
| `will_topic` | `` | Last will topic; no will is registered when empty |
| `will_payload` | `offline` | Last will payload |
| `will_qos` | `0` | QoS of the last will and of the birth message |
| `will_retain` | `true` | Retain flag of the last will and of the birth message |
| `birth_topic` | `` | Topic for the message published on every successful connect; falls back to `will_topic` |
| `birth_payload` | `online` | Birth payload |
| `tls_mode` | `none` | `tls` enables TLS |
| `tls_ca_certs` | `` | CA bundle; the system trust store is used when empty |
| `tls_certfile` | `` | Client certificate for mutual TLS |
| `tls_keyfile` | `` | Client key for mutual TLS |
| `tls_insecure` | `false` | `true` skips server hostname verification |
| `reconnect_delay_min` | `1` | Lower bound of the reconnect backoff, in seconds |
| `reconnect_delay_max` | `60` | Upper bound of the reconnect backoff, in seconds |
| `init_subscribe` | `` | Comma separated topics to subscribe to, each becoming a `DevString` attribute |
| `init_dynamic_attributes` | `` | JSON array of attribute descriptors, see below |

The connection is established without blocking, so a broker that is not up yet leaves the device
server running and reporting `FAULT` rather than aborting startup; paho reconnects on the configured
backoff. A broker that *refuses* the connection - a wrong password, for instance - puts the device
into `FAULT` with the reason in its status, instead of reporting it as `ON`.

The `connected` attribute reports whether the broker connection is currently up, `last_msg_at` when
the last message arrived.

# Attribute descriptors

`init_dynamic_attributes` carries a JSON array; every key but `name` is optional.

| Key | Default | Meaning |
| --- | --- | --- |
| `name` | - | Tango attribute name |
| `topic` | the `name` | MQTT topic, only needed when it differs from the attribute name |
| `modifier` | `` | Dotted path of a field inside a JSON payload, see below |
| `data_type` | `DevString` | `DevBoolean`, `DevLong`, `DevDouble`, `DevFloat` or `DevString` |
| `data_format` | `SCALAR` | `SCALAR`, `SPECTRUM` or `IMAGE` |
| `write_type` | `READ_WRITE`, or `READ` when a `modifier` is set | `READ`, `WRITE` or `READ_WRITE` |
| `qos` | `default_qos` | `0`, `1` or `2` |
| `retain` | `default_retain` | Retain flag used when this attribute is written |
| `unit`, `label` | `` | Attribute properties |
| `min_value`, `max_value` | `` | Attribute properties |
| `min_alarm`, `max_alarm` | `` | Attribute properties |
| `min_warning`, `max_warning` | `` | Attribute properties |

A `SPECTRUM` or `IMAGE` attribute carries its payload as a JSON array.

## Reading fields out of a JSON payload

A device that publishes one JSON document per topic is mapped by giving each attribute a `modifier`,
the dotted path of the field it reads. Attributes sharing a topic are all updated from a single
message, so the `topic` has to be named separately from the attribute `name`:

```json
[
  {"name": "temperature", "topic": "plant/sensor", "modifier": "temp",       "data_type": "DevDouble", "unit": "C"},
  {"name": "humidity",    "topic": "plant/sensor", "modifier": "hum",        "data_type": "DevLong"},
  {"name": "profile",     "topic": "plant/sensor", "modifier": "values",     "data_type": "DevDouble", "data_format": "SPECTRUM"},
  {"name": "inlet",       "topic": "plant/sensor", "modifier": "ports.0.id", "data_type": "DevString"}
]
```

A path segment addressing a JSON array is its index. Such an attribute is read only: publishing a
single field back would mean rebuilding the whole document, and the other fields in it belong to the
publisher, so a write is refused rather than allowed to clobber them.

Without a `modifier` the attribute name is the topic and the payload is the value, which is the
original behaviour and stays the default.

## Availability

`will_topic` together with `birth_payload` gives the usual online/offline signalling: the broker
publishes the will when the connection drops, and the driver publishes the birth message on every
successful connect. Configuring only a will would leave the retained `offline` payload standing as
the last word on that topic, so the birth message defaults to the will topic.

# Commands

| Command | Argument | Meaning |
| --- | --- | --- |
| `subscribe` | topic | Subscribe to a topic, with the strongest QoS its attributes asked for |
| `publish` | `[topic, value]`, optionally `[topic, value, qos, retain]` | Publish a value |
| `add_dynamic_attribute` | attribute name | Add an attribute at runtime, subscribing straight away when connected |

# Tests

```bash
python test_mqtt.py
```

Standalone script, no test runner. It drives the real driver methods through a state stub, so the
conversion, dispatch and connection handling under test is the code that runs in production.
